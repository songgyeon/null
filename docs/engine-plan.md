# 생성 엔진 계획 (미구현)

이 문서는 **결정만** 적는다. 구현은 UI 작업이 끝난 뒤 별도 커밋에서 시작한다.
지금 `worker.js`는 여전히 단일 호출이고, 이 문서의 어떤 것도 아직 코드에 없다.

---

## 확정 모델

| 단계 | 모델 |
|---|---|
| Writer | `claude-haiku-4-5` |
| Normal Director | `claude-sonnet-4-5-20250929` |
| Canon Critic | `claude-haiku-4-5` |
| Character Critic | `claude-haiku-4-5` |
| Critical Finalizer | `claude-sonnet-4-5-20250929` |

NULL은 Haiku 4.5 + Sonnet 4.5 하이브리드로 간다.

Sonnet 4.6과 Sonnet 5는 이 엔진에서 쓰지 않는다. 실패했을 때 조용히 넘어가지도
않는다. **모델이 바뀌면 캐릭터의 말맛이 바뀐다.** 4.5를 못 쓰면 실제 오류와
재시도 상태를 돌려준다.

모델 ID는 각 함수에 직접 쓰지 않는다. 설정 한곳에서 관리해서, 나중에 4.5가
종료되더라도 설정과 평가 자료만 갈아끼우면 되게 한다.

> 지금 `worker.js`의 `MODELS`는 4.6이 1순위이고 실패하면 다음 모델로 넘어간다.
> 엔진 커밋에서 그 폴백을 걷어내야 한다 — 위의 「자동 전환 금지」와 정면으로 어긋난다.

---

## 1. 일반 대화

```
TurnPacket 생성 — 코드
→ Writer — Haiku 4.5
→ Hard Filter와 Soft Signal — 코드
→ Director — Sonnet 4.5
→ 최종 검사 — 코드
→ Director가 고른 Haiku 후보를 그대로 출력
```

일반 턴에서 Sonnet 4.5는 **대사를 쓰지 않는다.** 후보를 비교해 아래 하나만 돌려준다.

```json
{ "decision": "A", "reject_codes": { "A": [], "B": ["TOO_EXPLANATORY"] } }
```

허용되는 `decision`은 `A` · `B` · `RETRY`뿐이다. Director는 후보를 고치거나, 둘을
합치거나, 새 대사를 만들 수 없다. 고른 후보를 코드가 그대로 최종 검사한 뒤 화면에 낸다.

둘 다 부족하면 `RETRY`와 실패 코드만 Writer에게 넘긴다. 재생성은 **최대 한 번.**
계속 실패하면 가짜 데모 대사로 덮지 말고 실제 재시도 UI를 쓴다.

## 2. Director 입력

Director에게 Writer의 프롬프트 전체를 다시 주지 않는다. 작은 `DirectorPacket`만 준다.

```
현재 화자 / 관계 단계 / 시간과 장소
이번 턴과 직접 관련된 fact_id
화자가 아는 범위
최근 관련 대화 4~6턴
코드가 감지한 soft signal
후보 A / 후보 B
```

사진 전체 목록, 아이템 전체 목록, 모든 장소 규칙, 전체 세계관, 전체 대화 기록,
지금 장면과 무관한 과거는 **넣지 않는다.** 고정 판단 기준과 출력 스키마만 고정 prefix로 둔다.

정보가 모자라 정사를 추측하게 만들지는 말되, Writer의 거대한 프롬프트를 그대로 복제하지도 않는다.

## 3. 중요 장면

```
CriticalScenePacket 생성 — 코드
→ Writer — Haiku 4.5
→ Hard Filter — 코드
→ Canon Critic ┐
               ├ Haiku 4.5 병렬
→ Character Critic ┘
→ Finalizer — Sonnet 4.5
→ 최종 검사와 상태 반영 — 코드
→ 출력
```

중요 장면에서는 일반 Director를 따로 부르지 않는다. Sonnet 4.5 Finalizer가 후보 선택과
최종 문장 완성을 함께 맡는다.

Finalizer를 Sonnet 4.5로 둔 까닭은, 중요한 장면에서는 정확성만큼 감정의 체온·서브텍스트·
머뭇거림·미련·말하지 않은 부분이 중요하기 때문이다. 정사와 상태는 앞 단계의 코드와
Canon Critic이 붙잡고, Character Critic은 관계 속도와 캐릭터 붕괴를 본다. Finalizer는
그 경계 안에서 유저가 실제로 읽을 대사의 말맛을 완성한다.

Finalizer가 할 수 있는 것: 후보 하나를 그대로 선택 / 후보 하나를 뼈대로 최소 수정 /
모두 부족하면 같은 반응 의도를 유지하며 새로 작성.

다만 `CriticalScenePacket`에 없는 사건·과거·유저 행동·유저 감정·관계 상태는 만들 수 없다.
Finalizer 결과도 반드시 같은 코드 검사를 다시 통과한다.

## 4. 중요 장면 라우팅

코드가 이벤트와 상태 전환으로 결정한다.

```
핵심 기억 최초 공개 / NULL 정체성이 직접 작동하는 장면
고백 수락 또는 거절 / 관계의 비가역적 변경
partner_id 확정 / D-0 선택 / 선택 직후 첫 반응
다른 캐릭터가 선택 사실을 처음 인지하는 장면
이별·떠남·재회 / 엔딩 분기 / 핵심 갈등의 비가역적 결과
```

모델의 `route_hint`만으로 중요 경로를 확정하지 않는다. 코드가 허용된 열거형 사유와
현재 상태를 확인한 뒤 승인한다.

단순한 질투, 가벼운 플러팅, 평범한 다툼, 선물, 장소 이동은 올리지 않는다.
**평소의 설렘과 재미는 일반 경로에서도 나와야 한다.**

## 5. Writer 프롬프트

Haiku Writer에게 규칙만 더 쌓지 않는다. 선택 엔진은 두 후보에 없는 설렘을 만들 수 없다.
그래서 각 캐릭터가 지금 관계 단계에서 취할 수 있는 행동과 주목할 재료를 보강한다.

재언:
```
감정이 새는 장소와 순간
돌봄으로 환원되지 않는 욕망·회피·질투
상대를 붙잡지만 인정하지 않는 방식
말하지 않고 남겨두는 행동
관계가 깊어질수록 가능해지는 행동
```

민현:
```
지금 유저에게서 실제로 관찰할 수 있는 구체적인 대상
말꼬리 잡기 외에 상대를 붙잡는 방법
장난 뒤에 확인하려는 실제 내용
불안할 때 달라지는 대사 길이와 행동
상대 반응에 따라 철수하거나 한 번 더 다가가는 조건
```

고정 대사를 대량 추가하는 작업이 아니다. 상황에 따라 Haiku가 즉흥적으로 조합할
**행동 어휘**를 주는 작업이다.

## 6. 후보 수

두 개가 무조건 한 개보다 낫다고 가정하지 않는다. `candidate_count=1`과 `2`를
교체 가능하게 구현하고 최소한 이 셋을 비교한다.

```
Haiku 한 호출에서 후보 1개
Haiku 한 호출에서 후보 2개
Haiku를 두 번 병렬 호출해 후보 하나씩
```

한 후보 방식에서는 Director가 `ACCEPT` / `RETRY`를, 두 후보 방식에서는 `A` / `B` / `RETRY`를
판단한다. 후보가 늘면 Writer 출력뿐 아니라 Director·Critic·Finalizer의 **입력에도 다시 과금**된다.

## 7. 코드 검사

**Hard Filter** — 코드가 정답을 명백히 아는 것만 자동 탈락.

```
스키마 오류 / 빈 응답 / 허용되지 않은 화자
내부 JSON 또는 검수 문구 노출
존재하지 않는 사진·장소·아이템
이미 소비된 일회성 이벤트 / 허용되지 않은 상태 변경
partner_id 충돌 / 직접적으로 동일한 대사 반복
```

**Soft Signal** — 문자열만으로 의미를 확정하기 어려운 것은 Director에게 신호로 넘긴다.

```
최근 대사와 유사함
질문으로 끝나는 반응이 연속됨
상담사·도우미 문구와 유사함
유저 행동을 날조했을 가능성
유저 감정을 확정했을 가능성
같은 의미를 표현만 바꿔 반복했을 가능성
```

n-gram, 물음표 비율, 문구 목록은 **참고 신호**다. 자연어 의미까지 코드가 정확히
판정한다고 가정하지 않는다.

## 8. 비용과 로그

이 하이브리드가 지금의 단일 Sonnet 호출보다 싸다고 미리 단정하지 않는다.
지금 로그에는 usage가 없다. 실험 전에 호출 단계별로 기록한다.

```
request_id / stage / model
input_tokens / output_tokens
cache_read_input_tokens / cache_creation_input_tokens
latency_ms / attempt / scene_tier
```

대화 원문과 전체 프롬프트는 로그에 추가로 저장하지 않는다.

```
B = 현재 Sonnet 단일 생성 평균 비용
N = 일반 턴 — Haiku Writer + Sonnet 4.5 Director 평균 비용
K = 중요 턴 — Haiku Writer + Haiku Critics + Sonnet 4.5 Finalizer 평균 비용

중요 턴 비율이 p일 때   NEW = (1 - p) × N + p × K
```

호출 수만 보고 비용을 추측하지 않는다. 후보 재입력, 캐시 쓰기·읽기, RETRY 비용까지 포함한다.

## 9. 품질 비교

지금 경로를 바로 지우지 말고 기능 플래그 뒤에 기준선으로 남긴다.

```
캐릭터 이름 없이도 누군지 구별되는가
설정 오류 / 유저 행동·감정 날조 / 상담사 말투
반복과 질문 비율 / 관계 속도
다음 대화를 당기는가 / 설렘과 재미
평균 비용 / 평균 latency / 일반 턴 p95 / 중요 턴 p95
```

Director와 Finalizer의 판단 기준은 NULL 실제 대화로 조정한다.
일반 챗봇의 친절함·도움·상세함을 좋은 대사의 기준으로 쓰지 않는다.

## 10. 실패와 폴백

```
Sonnet 4.5 실패
→ Sonnet 4.6 자동 전환 금지
→ Sonnet 5 자동 전환 금지
→ 데모 대사 출력 금지
→ 실제 오류 상태와 재시도
```

같은 논리 요청을 재시도할 때는 `request_id`를 유지하고, 이미 성공한 단계가 있으면
가능한 범위에서 중복 과금을 막는다.

## 11. 지금 UI에서 할 일

엔진은 아직 구현하지 않는다. 지금은 이것만 한다.

```
Expo 확인 화면
전송마다 request_id 생성
재시도할 때 논리 요청 ID 유지
최종 응답까지 busy 상태 유지
늦게 도착한 이전 응답 차단
짧은 강제 타임아웃을 추가하지 않음
오류와 사용자 취소 구분
```

`request_id`의 Worker 멱등 처리는 UI와 **다른 커밋**으로 분리한다.
UI는 호출 횟수나 모델 종류를 전제하지 않고 최종 응답 하나만 받는다.
후보, Director 판정, Critic 결과는 화면에 절대 노출하지 않는다.

## 최종 원칙

```
코드가 세계의 사실을 결정한다.
Haiku 4.5가 살아 있는 반응을 탐색한다.
일반 턴에서는 Sonnet 4.5가 감정적으로 더 맞는 후보를 선택한다.
중요한 장면에서는 Sonnet 4.5가 직접 최종 대사를 완성한다.
모델의 우수성과 비용은 추측이 아니라 실제 NULL 대화와 usage로 판단한다.
```
