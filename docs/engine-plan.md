# 생성 엔진

결정과 그 결정이 코드에서 어디에 사는지를 적는다.

## 지금 상태

| | |
|---|---|
| 일반 턴 | ✅ 쓰는 쪽 후보 → 코드 검사 → 고르는 쪽 선택 |
| 중요 장면 | ✅ 쓰는 쪽 → 검사 둘 병렬 → 마무리 |
| 라우팅 | ✅ 코드가 열거형 사유 + 상태로 승인 |
| 폴백 금지 | ✅ 대사 길에서 목록 폴백 제거 |
| 후보 수 | ✅ one / pair / parallel 교체 가능 |
| 단계별 실측 | ✅ 응답의 `stages`, 화면 콘솔에도 |
| 기준선 | ✅ `ENGINE_MODE=legacy` 깃발 뒤 |
| 오프라인 eval | ✅ `node tools/eval.mjs` (눈은 `tools/eval-eye.mjs` — 워커와 갈라져 있다) |
| 실제 대화로 기준 조정 | ⬜ 굴려보고 나서 |

| 무엇 | 어디 |

## 확정 모델

| 단계 | 모델 |
|---|---|
| Writer | `claude-haiku-4-5` |
| Normal Director | `claude-haiku-4-5` |
| Canon Critic | `claude-haiku-4-5` |
| Character Critic | `claude-haiku-4-5` |
| Critical Finalizer | `claude-sonnet-4-5-20250929` |

NULL은 Haiku 4.5 + Sonnet 4.5 하이브리드로 간다.
**위를 쓰는 자리는 하나뿐이다 — 중요 장면의 마무리.**

> Normal Director는 원래 Sonnet 4.5였다. 그러면 「중요할 때만 Sonnet」이 아니라
> **일반 턴마다 Sonnet을 부르는 것**이 된다. 계약과 실제가 어긋나 있었고,
> `test/run.mjs`의 「고르는 쪽과 마무리는 같은 급이다」가 그 어긋남을 강제하고
> 있었다. 코드·문서·테스트·비용식을 함께 고쳤다(테스트 이름은 「마무리만 위를 쓴다」).
> 고르는 일은 **쓰는 일보다 쉬운 일**이다 — 후보 둘 중 하나를 고르고 코드를
> 붙이는 데 위가 필요한지는 증명된 적이 없다. G의 세 갈래 비교가 답한다.

Sonnet 4.6과 Sonnet 5는 이 엔진에서 쓰지 않는다. 실패했을 때 조용히 넘어가지도
않는다. **모델이 바뀌면 캐릭터의 말맛이 바뀐다.** 4.5를 못 쓰면 실제 오류와
재시도 상태를 돌려준다.

모델 ID는 각 함수에 직접 쓰지 않는다. 설정 한곳에서 관리해서, 나중에 4.5가
종료되더라도 설정과 평가 자료만 갈아끼우면 되게 한다.

> ✅ 걷었다. `MODELS`의 순차 폴백이 남은 데는 둘뿐이다 — 말맛과 무관한
> 뒷일(요약)과, 깃발 뒤의 기준선(옛 길). 대사를 만드는 지금 길은 그 목록을
> 안 본다. 못 쓰면 진짜 오류를 돌려주고 화면에 재시도가 뜬다.

## 1. 일반 대화

```
TurnPacket 생성 — 코드
→ Writer — Haiku 4.5
→ Hard Filter와 Soft Signal — 코드
→ Director — Haiku 4.5
→ 최종 검사 — 코드
→ Director가 고른 Haiku 후보를 그대로 출력
```

일반 턴은 **호출 둘이 전부다.** Director는 **대사를 쓰지 않는다.** 후보를 비교해
아래 하나만 돌려준다.

```json
{ "decision": "A", "reject_codes": { "A": [], "B": ["TOO_EXPLANATORY"] } }
```

허용되는 `decision`은 `A` · `B` · `RETRY`뿐이다. Director는 후보를 고치거나, 둘을
합치거나, 새 대사를 만들 수 없다. 고른 후보를 코드가 그대로 최종 검사한 뒤 화면에 낸다.

둘 다 부족하면 `RETRY`와 실패 코드만 Writer에게 넘긴다. 재생성은 **최대 한 번.**
계속 실패하면 가짜 데모 대사로 덮지 말고 실제 재시도 UI를 쓴다.

## 2. Director 입력

Director에게 Writer의 프롬프트 전체를 다시 주지 않는다. 작은 `DirectorPacket`만 준다.

```
현재 화자 / 관계 단계 / 시간과 장소
이번 턴과 직접 관련된 fact_id
화자가 아는 범위
최근 관련 대화 4~6턴
코드가 감지한 soft signal
후보 A / 후보 B
```

사진 전체 목록, 아이템 전체 목록, 모든 장소 규칙, 전체 세계관, 전체 대화 기록,
지금 장면과 무관한 과거는 **넣지 않는다.** 고정 판단 기준과 출력 스키마만 고정 prefix로 둔다.

정보가 모자라 정사를 추측하게 만들지는 말되, Writer의 거대한 프롬프트를 그대로 복제하지도 않는다.

## 3. 중요 장면

```
CriticalScenePacket 생성 — 코드
→ Writer — Haiku 4.5
→ Hard Filter — 코드
→ Canon Critic ┐
               ├ Haiku 4.5 병렬 — 각각 한 호출로 후보 전부를 본다
→ Character Critic ┘
→ Finalizer — Sonnet 4.5
→ 최종 검사와 상태 반영 — 코드
→ 출력
```

중요 장면은 **호출 넷이다**(재시도 포함 최대 여덟). **검사는 후보마다 부르지
않는다** — Canon 한 호출과 Character 한 호출이 각각 A/B를 함께 보고, 결과 안에
후보 표식(`candidate`)을 남긴다. 후보마다 부르면 여섯 호출이 나고, 결과를
합치면서 어느 후보의 문제였는지가 사라진다.

중요 장면에서는 일반 Director를 따로 부르지 않는다. Sonnet 4.5 Finalizer가 후보 선택과
최종 문장 완성을 함께 맡는다.

Finalizer를 Sonnet 4.5로 둔 까닭은, 중요한 장면에서는 정확성만큼 감정의 체온·서브텍스트·
머뭇거림·미련·말하지 않은 부분이 중요하기 때문이다. 정사와 상태는 앞 단계의 코드와
Canon Critic이 붙잡고, Character Critic은 관계 속도와 캐릭터 붕괴를 본다. Finalizer는
그 경계 안에서 유저가 실제로 읽을 대사의 말맛을 완성한다.

Finalizer가 할 수 있는 것: 후보 하나를 그대로 선택 / 후보 하나를 뼈대로 최소 수정 /
모두 부족하면 같은 반응 의도를 유지하며 새로 작성.

다만 `CriticalScenePacket`에 없는 사건·과거·유저 행동·유저 감정·관계 상태는 만들 수 없다.
Finalizer 결과도 반드시 같은 코드 검사를 다시 통과한다.

## 4. 중요 장면 라우팅

코드가 이벤트와 상태 전환으로 결정한다.

```
핵심 기억 최초 공개 / NULL 정체성이 직접 작동하는 장면
고백 수락 또는 거절 / 관계의 비가역적 변경
partner_id 확정 / D-0 선택 / 선택 직후 첫 반응
다른 캐릭터가 선택 사실을 처음 인지하는 장면
이별·떠남·재회 / 엔딩 분기 / 핵심 갈등의 비가역적 결과
```

모델의 `route_hint`만으로 중요 경로를 확정하지 않는다. 코드가 허용된 열거형 사유와
현재 상태를 확인한 뒤 승인한다.

단순한 질투, 가벼운 플러팅, 평범한 다툼, 선물, 장소 이동은 올리지 않는다.
**평소의 설렘과 재미는 일반 경로에서도 나와야 한다.**

## 5. Writer 프롬프트

Haiku Writer에게 규칙만 더 쌓지 않는다. 선택 엔진은 두 후보에 없는 설렘을 만들 수 없다.
그래서 각 캐릭터가 지금 관계 단계에서 취할 수 있는 행동과 주목할 재료를 보강한다.

재언:
```
감정이 새는 장소와 순간
돌봄으로 환원되지 않는 욕망·회피·질투
상대를 붙잡지만 인정하지 않는 방식
말하지 않고 남겨두는 행동
관계가 깊어질수록 가능해지는 행동
```

민현:
```
지금 유저에게서 실제로 관찰할 수 있는 구체적인 대상
말꼬리 잡기 외에 상대를 붙잡는 방법
장난 뒤에 확인하려는 실제 내용
불안할 때 달라지는 대사 길이와 행동
상대 반응에 따라 철수하거나 한 번 더 다가가는 조건
```

고정 대사를 대량 추가하는 작업이 아니다. 상황에 따라 Haiku가 즉흥적으로 조합할
**행동 어휘**를 주는 작업이다.

## 6. 후보 수

두 개가 무조건 한 개보다 낫다고 가정하지 않는다. `candidate_count=1`과 `2`를
교체 가능하게 구현하고 최소한 이 셋을 비교한다.

```
Haiku 한 호출에서 후보 1개
Haiku 한 호출에서 후보 2개
Haiku를 두 번 병렬 호출해 후보 하나씩
```

한 후보 방식에서는 Director가 `ACCEPT` / `RETRY`를, 두 후보 방식에서는 `A` / `B` / `RETRY`를
판단한다. 후보가 늘면 Writer 출력뿐 아니라 Director·Critic·Finalizer의 **입력에도 다시 과금**된다.

## 7. 코드 검사

**Hard Filter** — 코드가 정답을 명백히 아는 것만 자동 탈락.

```
스키마 오류 / 빈 응답 / 허용되지 않은 화자
내부 JSON 또는 검수 문구 노출
존재하지 않는 사진·장소·아이템
이미 소비된 일회성 이벤트 / 허용되지 않은 상태 변경
partner_id 충돌 / 직접적으로 동일한 대사 반복
```

**Soft Signal** — 문자열만으로 의미를 확정하기 어려운 것은 Director에게 신호로 넘긴다.

```
최근 대사와 유사함
질문으로 끝나는 반응이 연속됨
상담사·도우미 문구와 유사함
유저 행동을 날조했을 가능성
유저 감정을 확정했을 가능성
같은 의미를 표현만 바꿔 반복했을 가능성
```

n-gram, 물음표 비율, 문구 목록은 **참고 신호**다. 자연어 의미까지 코드가 정확히
판정한다고 가정하지 않는다.

## 8. 비용과 로그

이 하이브리드가 지금의 단일 Sonnet 호출보다 싸다고 미리 단정하지 않는다.
실험 전에 호출 단계별로 기록한다. ✅ 응답의 `stages`가 이 줄들이다.

```
request_id / call_id / stage / model / candidate
input_tokens / output_tokens
cache_read_input_tokens / cache_creation_input_tokens
latency_ms / attempt / status / scene_tier
```

`call_id`가 있는 까닭은 중요 장면이 네 단계이고 재시도가 붙기 때문이다 —
단계 이름만으로는 같은 이름이 두 번 나올 때 구분이 안 된다.

**계측은 요청별이다.** 모듈 전역(`stageLog`/`lastUsage`)이던 때는 아이솔레이트
하나가 요청을 동시에 받으면 A 요청의 단계가 B 응답에 실렸다 — 비용도 지연도
믿을 수 없었다. 요청 진입에서 `newMeter(request_id)`를 만들어 들고 다닌다.

`usage`는 예나 지금이나 **쓰는 쪽 한 번의 실측**이다. 총합은 `usage_total`로
**따로** 낸다 — 기존 `usage`의 뜻을 몰래 총합으로 바꾸면 옛 화면이 읽던 숫자가
딴것이 된다.

> `request_id`는 **멱등 키가 아니다.** 늦은 응답을 가리는 이름표일 뿐이라,
> 같은 ID로 재시도하면 모델을 다시 부르고 비용이 또 난다.

**대화 원문과 전체 프롬프트는 로그에 남기지 않는다.** 쓰는 쪽 응답 600자를 매 턴
찍고 있었는데 그건 대화 원문이다. 대시보드에서 `DEV_LOG=1`을 켰을 때만 찍는다.
기본 로그에 남는 것은 단계·토큰·지연·오류 코드뿐이다.

```
B = 현재 Sonnet 단일 생성 평균 비용
N = 일반 턴 — Haiku Writer + Haiku Director 평균 비용   (호출 2)
K = 중요 턴 — Haiku Writer + Haiku Critic ×2 + Sonnet 4.5 Finalizer 평균 비용   (호출 4)

중요 턴 비율이 p일 때   NEW = (1 - p) × N + p × K
```

호출 수만 보고 비용을 추측하지 않는다. 후보 재입력, 캐시 쓰기·읽기, RETRY 비용까지 포함한다.
재시도가 붙으면 중요 턴은 최대 여덟 호출이 되고, 그것도 `stages`에 그대로 잡힌다.

## 8.5 지식 범위 — C·E단계 계약 (결정됨, 미구현)

선물 하나가 사람마다 **다른 사실**을 낳는다. 유저와 재언은 출처까지 알고,
민현은 물건이 거기 있다는 것만 안다. 그래야 「삼촌, 그거 어디서 났어요?」가
나온다. Fact 둘로 가르는 것으로 충분하고 0단계 계약은 안 고친다.

```
gift_source_fact   유저가 재언에게 머그컵을 줬다     known_by: user, jaeeon
item_holder_fact   머그컵이 재언에게 있다            known_by: user, jaeeon, minhyun
disclosure         {fact_id, by, heard_by, room, at}
```

**`known_by: user`는 「유저가 아는 사실」일 뿐이다.** 방에 유저가 있다는
이유만으로 인물 프롬프트에 넣으면 안 된다. 유저가 그 방에서 실제로 말했는지는
`disclosure`로 따로 관리하고, **`by`가 그 Fact를 실제로 알고 `heard_by`가 그
자리에 있었을 때만** 승인한다.

**모든 단톡 턴을 화자별 호출로 바꾸지 않는다.** 비용이 늘고 구조가 과해진다.
일반 단톡·관전은 기존 한 호출을 유지하고, **정보가 비대칭인 사건만** 화자
순차 경로를 쓴다. Sonnet까지 갈 자리가 아니다 — Haiku 두 호출이면 된다.

```
선물 관측 사건일 때만
  ① Haiku 민현   자기 known_by만 받는다        → 「삼촌, 그거 어디서 났어요?」
  ② Haiku 재언   자기 known_by + 민현의 실제 대사  → 「책상 위에 있었으면 그냥 두지 그랬어요.」
반대 방향이면 순서와 말투가 바뀐다
  ① 재언 「그거 책상 위에 있던데.」 → ② 민현 「봤어요?」
```

한 프롬프트에 두 사람 몫을 나란히 넣고 「민현은 첫째를 모르는 척해」라고
적을 수도 있다. 모델이 지킬 가능성도 있다. 다만 그건 코드가 **보장**하는
것이 아니라 **부탁**하는 것이고, 이 엔진의 원칙은 「중요한 세계의 사실은
모델의 선의가 아니라 코드로 보장한다」다.

**Fact 이전에 이미 새고 있는 것 셋** — C·E에서 같이 고친다.

| | 무엇 | 어디 |
|---|---|---|
| 🔴 | `buildEvent(kind:"gift")`가 「선생님이 이재언에게 회색 머그컵을 줬다」를 관전방에 통째로 준다. Fact를 아무리 잘 가려도 이 줄이 살아 있으면 순효과가 0이다 | `worker.js` |
| 🔴 | `ROOM_EARS.health`가 죽은 배선이다. 관전(auto)은 payload에 `room`을 안 싣고 `ROOMS_OK`가 생성 경로에서 health를 안 받아 `room="minhyun"`으로 떨어진다 | `worker.js` · `app.js` · `app/lib/api.ts` |
| 🔴 | 테스트 「유저도 아는 일은 다른 방에서도 말할 수 있다」가 **그 누출을 정답으로 고정**해뒀다 | `test/run.mjs` |

## 8.6 저장과 연출의 경계 — 웹 (E-A에서 닫음)

E-A는 「제안 ≠ 발생」을 코드 모양으로 못박았다. 그런데 웹에는 그 뒤에
**시간**이 남아 있었다. 말풍선은 0.6초마다 하나씩 화면 상태로 붙고 저장은
리액트가 그림을 그린 뒤에 따라오는데, `effect_done`과 `ackScene`은 답이
오자마자 찍혔다. 그 사이가 열려 있었다.

```
답 도착 → effect_done 찍음 → ackScene(장면 소모) → …500ms… → 첫 말풍선
                     ↑ 여기서 새로고침하면
                       장면은 썼는데 답은 한 줄도 없고,
                       초대는 「처리했다」는 표만 남고 창은 영영 안 뜬다
```

순서를 뒤집었다. **답이 오면 먼저 통째로 적는다**(`null_batch`) — 말풍선
전부, 뒤따를 지문, 열어야 할 초대, 닫아야 할 자리. 그 다음에 장면을 지우고,
화면은 적힌 것을 재생만 한다. 재생 도중 꺼도 남은 것부터 다시 푼다.

| | 무엇 |
|---|---|
| 저장 순서 | 가방 → 덩어리(`null_batch`) → `effect_done`. 표가 제일 마지막이라 「표만 남는」 상태가 안 생긴다 |
| 멱등 | 말풍선 id를 **적을 때** 박는다(`batchItemId`). 재생 전에 그 방에 이미 있는지 보므로 저장이 어디서 끊겨도 두 번 안 붙는다 |
| 덮어쓰기 금지 | 같은 batch id가 이미 있으면 그대로 둔다(`putBatch`가 false). 반쯤 푼 상태를 처음으로 되돌리면 이미 뜬 말풍선이 또 뜬다 |
| 축출 금지 | `null_batch`는 완료 기록이 아니라 **미완료 장부**다. 상한을 두지 않는다 — `slice(-8)`이 아홉 번째에서 아직 안 푼 답을 조용히 지웠다 |
| 잠금 | 안 푼 덩어리가 있는 방은 `busy`이고 `send`가 막는다(`replaying`). 재생 중에 새 말을 받으면 순서가 갈리고 새 요청의 history에서 옛 답이 빠진다 |
| 초대 | `null_invite`는 **줄**이다. 두 방에서 초대가 겹쳐도 앞엣것이 안 사라진다 — 답해야 다음이 열린다 |
| 연출 시점 | `messages.length × 600ms` 짐작을 걷었다. 큐는 방마다가 아니라 하나뿐이라 다른 방 말풍선이 앞에 쌓이면 짐작이 어긋났다 — 이제 **그 덩어리의 마지막 말풍선이 실제로 뜬 자리**에 매단다 |

### `appendMsg`의 계약

즉시 저장하고 **갱신된 그 방의 목록을 돌려준다.** 저장에 실패하면 `null`이다.

```
const next = appendMsg(room, sys);      ← 이것만 쓴다
const next = [...storeRef.current.msgs[room], sys];   ← 금지
```

두 번째 꼴은 ref가 이미 갱신됐으므로 **같은 사건을 두 번** 싣는다. 화면과
저장소에는 한 번인데 모델에게 가는 history에는 두 번이고 `counts`도 부푼다 —
같은 일이 두 번 일어난 것으로 읽혀 관계 단계와 해금이 일찍 열린다. 여덟
특수 경로(자리 자동 종료 · 직접 나가기 · 귀갓길 · 초대 수락/거절 · 자리 이동 ·
지도 방문 · 선물 · 선물 들고 가기)가 전부 이 꼴이었다.

### 저장 실패 — write-ahead journal

「저장하고 나서 실패면 멈춘다」로는 부족했다. 실패를 알았을 때는 이미 앞
단계의 상태가 바뀐 뒤라 되돌릴 수도 이어갈 수도 없다: 가방은 들어갔는데
지문이 없고, 표는 찍혔는데 장부가 없고, 초대는 줄에서 빠졌는데 답 지문이
안 남았다. localStorage key 여럿을 하나씩 즉시 바꾸는 구조가 그렇다.

**순서를 뒤집는다. 바꿀 계획을 먼저 한 덩어리로 적고, 저장이 성공한 뒤에
`resumeBatch`가 그 계획을 실행한다.** 상태를 먼저 바꾸고 장부를 쓰는 자리는
없다 — 모델의 답도(`commitTurn`), 유저가 누르는 여덟 가지 일도(`localBatch`),
관전 자동 응답도 같은 장부를 탄다.

```
{ id, room, items, sys, effects, unlocked,
  scene_ack, invite_ops, local_ops, auto_event_id, toast }
```

실행은 전부 **쓰고 나서 다시 읽어 확인한다.** 그러면 「이미 되어 있다」와
「방금 했다」가 같은 검사로 처리되고, 되풀이해도 결과가 같다.

| | 무엇 |
|---|---|
| Effect 결과 | 참·거짓으로 뭉개지 않는다 — `applied` / `already_applied` / `not_applicable` / `storage_error{key}`. 「이미 가진 물건」과 「저장 실패」가 둘 다 false였던 것이 가방 없이 장면만 소모되던 자리다 |
| 소모는 나중에 | 말이 안 남았으면 거기서 멈춘다. 초대를 줄에서 빼는 것 · 장면 소모 · 관전 사건 소모는 전부 그 뒤다 |
| 지문 guard | 「누구에게 받았다」 줄에 `need:{key,from}`가 붙는다. 그 물건이 실제로 그 사람이 준 것으로 가방에 있을 때만 나온다 |
| 재시도 | 두 갈래다. **모델 답을 이미 받은 장부**(`commitTurn`·관전)는 이어서 풀기만 한다 — API 0회. `request_id`는 서버의 멱등 키가 아니라 다시 부르면 Writer·Critic·Finalizer 값이 통째로 한 번 더 난다. **아직 모델을 안 부른 장부**(초대·나가기·귀갓길·자리 이동·지도 방문·선물)는 장부를 다 푼 뒤 원래 요청을 정확히 한 번 이어간다 |
| `after_request` | 그 이어갈 요청은 closure가 아니라 **장부에 선언형으로** 적는다 — closure로 들고 있으면 새로고침 한 번에 사라져서, 선물은 가방에 들어갔는데 상대가 영영 아무 말도 안 하는 판이 된다. `history`·`counts`·가방은 적을 때가 아니라 **보낼 때** 최신 상태로 다시 조립한다 |
| 실패도 이름표 | 말풍선 저장 실패·`dropBatchItem` 실패·마지막 `dropBatch` 실패까지 전부 그 batch id와 함께 올라온다. 이름표를 잃으면 재시도가 무엇을 이을지 모르고, 삼키면 그 방이 영영 잠긴다 |
| 순서 보존 | 한 줄이 안 남으면 그 덩어리의 나머지를 큐에서 거둔다. 안 거두면 다음 줄이 먼저 떠서 이어 풀 때 순서가 뒤집힌다 |
| 화면 | **실패가 타이핑보다 앞선다.** 저장이 실패한 방은 「이어서 할 것이 남았다」는 뜻으로 잠긴 채(`busy`)로 두는데, 전에는 `busy`면 재시도 단추를 숨겨서 복구할 정보가 있는데도 누를 수가 없었다 |
| 관전 id | `auto:${event.id}#${i}` — 뽑기가 아니다. 둘째 말풍선 저장이 실패해도 다시 만들 때 첫째가 두 번 안 붙는다 |
| 잠금 | `replaying(room)`은 items가 아니라 **그 방에 미완료 장부가 있는지**를 본다. 말풍선이 끝났어도 뒤가 남았으면 입력을 안 연다 |

`saveStore` · `saveBag` · `saveInvites` · `saveBatches` · `saveEffDone` ·
`saveGifts` · `saveScene` · `saveMet` · `saveGone` · `saveGiftDay` ·
`saveScenePend` · `saveAutoQ`가 전부 성공 여부를 돌려준다.

### 검증

소스 모양이 아니라 **실제로 굴려서** 한다. `test/run.mjs`가 app.js의 논리부를
최소 리액트·가짜 시계·가짜 저장소 위에서 돌린다. 새로고침은 같은 저장소로
다시 켜는 것으로 흉내낸다. `Date`도 주입한다 — 타이머만 가짜로 두면 캐릭터
수면 판정이 진짜 벽시계를 봐서 실행 시각에 따라 통과와 실패가 갈렸다.
기준 시각은 로컬 벽시계 성분으로 만들어 어느 시간대에서도 화요일 오후 두 시다.

```
첫 말풍선 전 끄기 · 타이핑 도중 끄기 · 큐에 다른 방이 먼저 쌓인 상태
초대 복원 · 두 번 재생 · 여덟 경로의 사건 한 번 · 재생 중 입력 차단
같은 batch id 재commit · 미완료 아홉 개 · 두 방 초대 겹침
null_bag·null_batch·null_eff_done·null_invite·null_store_v1 각각 저장 실패
말풍선은 끝났고 뒤가 남은 장부에서도 입력 차단
여덟 경로 각각에 메시지 저장 실패 주입 — 도장·선물·자리가 먼저 소비되지 않는다
실패를 걷고 이어서 돌린 끝이 무실패 실행과 같다 · 복구 중 API 호출 0
관전 저장 실패 시 사건 미소모
말풍선 저장·장부에서 빼기·마지막 지우기를 각각 n번째 쓰기에서 실패
화면 조건 그대로 재시도 단추를 눌러 빠져나오기
local batch 복구 뒤 fetch 1회·캐릭터 답 1회 (여덟 경로 전부)
모델 답을 받은 batch 복구 뒤 fetch 0회
끝나면 장부 0 · failed 없음 · busy false · 중복 메시지 없음
```

**아직 안 닫은 것 (E-A를 막지는 않는다)**

| | 무엇 |
|---|---|
| 🟠 | Expo의 `null_eff_done` 저장이 비동기라 같은 턴에 두 Effect가 겹치면 경쟁이 난다. 웹은 동기라 해당 없음 |
| 🟠 | 관전 자동 사건 큐 `null_auto_q`의 `slice(-20)`이 밀린 옛 사건을 조용히 버린다 |
| 🟠 | Expo는 아직 이 장부를 안 쓴다. 웹을 기준으로 삼기로 한 범위 결정(E 절) 그대로다 |
| 🔴 | **`story_transition`은 실제 상태 적용을 만든 뒤에만 방출한다.** 지금 클라이언트는 스키마만 받고 id를 적을 뿐이다 — E-B에서 워커가 이걸 내기 전에 적용부터 만든다 |

## 9. 품질 비교

지금 경로를 바로 지우지 말고 기능 플래그 뒤에 기준선으로 남긴다.
✅ `ENGINE_MODE=legacy`. 같은 대화를 두 길로 굴려서 나란히 볼 수 있다.

명백한 것은 `node tools/eval.mjs`가 센다 — 앱에서 내보낸 기록을 읽어
안이 비친 줄·상담사 말투·메아리·금지한 어미·긴 줄·유저 속을 단정한 것·
같은 말 반복·옛 정사의 흔적을 세고, 인물별 평균 문장 길이도 같이 낸다.
위 모델과 비교해서 통과 여부를 정하지 않는다 — 그건 「비싼 쪽이 정답」이라는
말이고 이 게임에서는 틀렸다. 기준은 바깥이 아니라 작품 안에 있다.

### 자는 생산 코드와 다른 눈을 쓴다

전에는 자가 워커의 `isLeak`/`isMeta`를 그대로 가져다 썼다. 판정을 한 군데로
모으는 것은 보통 옳지만 **여기서는 틀렸다.**

```
워커 필터가 못 본다 → 자가 같은 필터를 빌려 쓴다 → 자도 못 본다
→ 둘이 동시에 「문제 없음」이라고 한다
```

실제로 그런 줄이 있었다(`update성의 없다고 놀린 게 아니라…`). 사람이 손으로
찍어둔 골든 정답지만 그게 문제라고 알려줬다.

그래서 자의 눈을 `tools/eval-eye.mjs`로 갈랐다. **worker.js를 import하지
않는다** — 테스트가 그걸 강제한다. 축도 다르다: 워커는 **문구 목록**으로 보고
(「The instructions」·「유저」), 자는 **문자 구성**으로 본다(대소문자, 로마자와
한글이 붙은 자리, 조각의 모양). 같은 것을 두 번 보는 게 아니라 다른 각도에서 본다.

워커의 눈은 **엇갈림**을 재는 데만 쓴다. 자는 보는데 워커가 못 보면 그게
D단계에서 고칠 목록이고, 반대면 자를 고칠 목록이다. `node tools/eval.mjs`의
「엇갈림」 줄에 나온다.

### 무엇으로 나누나

「100발화 줄당」은 **줄바꿈을 적게 하는 모델이 유리해진다.** 한 턴에 네 줄을
쓰는 모델과 두 줄을 쓰는 모델이 같은 실수를 하면 줄당 수치가 두 배 차이 난다.
그래서 **사건과 턴**으로 나눈다.

```
방별          재언 · 민현 · 단톡 · 관전 각각의 발화·턴·걸린 것
응답 턴당     오류가 든 턴의 비율 (연속된 인물 발화 한 덩어리가 한 턴)
사건당        주고받은 사건당 부정 횟수 (지문에서 뽑는다)
줄당          참고로만 남긴다
```

읽는 자(`readLog`)가 **지문과 줄머리 시각을 안 버린다.** 지문이 이 판에서
실제로 일어난 사건이고(선물·자리 이동), 사건당으로 나누려면 그게 있어야 한다.

### 아직 안 재는 것

```
기억 공개 사건당 정사 부정     텍스트 기록에 장면 갈래가 안 실린다 → G3 trace JSON
중요 장면당 올바른 라우팅       같은 이유 → G3 trace JSON
시각 어긋남                     내보내기 시각이 게임 시계가 아니라 현실 시각이다 → F단계 뒤
```

억지로 재는 척하지 않는다. 못 재면 못 잰다고 적는다.

### 자를 먼저 잰다

자를 고치면 숫자는 언제나 좋아진다. 그게 실제 개선인지 자가 눈이 먼 것인지는
두 정답지가 답한다.

```
docs/golden/<기록>.tsv     잡아야 할 것 — 사람이 눈으로 찾아 줄번호로 박은 것
docs/dialogue-corpus.md    잡으면 안 되는 것 — 작가가 쓴 2,640줄은 전부 정답이다
```

작가 문구집을 오탐 시험대로 쓰는 것이 실제로 두 번 일했다.
`-(으)ㄹ래요`(「먹을래요」)를 전언 어미로 잡고 있었고, 「선생님 하고 싶은 대로
해도 돼요」를 「유저를 대신 쓴 것」으로 잡고 있었다. 둘 다 기록에는 없고
문구집에만 있던 갈래다.

### 반례도 정답지다

작가 문구집에서 오탐 0을 확인하고 「됐다」고 했는데, 그건 **없는 것을 안
잡는다**는 뜻이지 앞으로도 안 잡는다는 뜻이 아니었다. 아직 쓰이지 않은
정상 대사를 지어내 쳐보니 스물세 건이 걸렸다 — 하필 이 게임의 주 화제인
음악과 SNS였다(`se so neon` · `girl in red` · `mp3로` · `minhyunee_2예요`).

그 스물셋을 `docs/golden/_normal.tsv`에 박았다. 이제 오탐 0은 한 번 잰
수치가 아니라 **테스트가 지키는 성질**이다.

### 둘 중 하나는 잡는다

자와 워커가 서로 다른 것을 놓친다. 지켜야 하는 것은 「자가 잡는다」가
아니라 **「둘 중 하나는 잡는다」**다 — 둘 다 못 보는 것이 이 구조가 막으려는
유일한 것이다. 교차검사 테스트가 그 성질을 굳힌다.

```
update성의 …          자만 봄     → 워커를 고칠 목록(D단계)
I should probably …   워커만 봄   → 자를 고칠 목록
```

「워커가 잡으니 괜찮다」로 넘어가지 않는다. 워커가 정말 잡는지를 테스트가 센다.

「설레는가」와 「이름 없이도 누군지 구별되는가」는 이 자가 못 잰다.
그건 사람이 읽어야 하고, 이 자는 그 읽기 전에 명백한 것을 걸러내는 자다.

```
캐릭터 이름 없이도 누군지 구별되는가
설정 오류 / 유저 행동·감정 날조 / 상담사 말투
반복과 질문 비율 / 관계 속도
다음 대화를 당기는가 / 설렘과 재미
평균 비용 / 평균 latency / 일반 턴 p95 / 중요 턴 p95
```

Director와 Finalizer의 판단 기준은 NULL 실제 대화로 조정한다.
일반 챗봇의 친절함·도움·상세함을 좋은 대사의 기준으로 쓰지 않는다.

## 10. 실패와 폴백

```
Sonnet 4.5 실패
→ Sonnet 4.6 자동 전환 금지
→ Sonnet 5 자동 전환 금지
→ 데모 대사 출력 금지
→ 실제 오류 상태와 재시도
```

같은 논리 요청을 재시도할 때는 `request_id`를 유지하고, 이미 성공한 단계가 있으면
가능한 범위에서 중복 과금을 막는다.

## 11. UI 쪽 계약

엔진과 무관하게 UI가 지켜야 하는 것들. 전부 되어 있다.

```
Expo 확인 화면
전송마다 request_id 생성
재시도할 때 논리 요청 ID 유지
최종 응답까지 busy 상태 유지
늦게 도착한 이전 응답 차단
짧은 강제 타임아웃을 추가하지 않음
오류와 사용자 취소 구분
```

`request_id`의 Worker 멱등 처리는 아직 없다 — 지금은 답에 그대로 비춰주기만
하고, 늦게 온 답을 가리는 판정은 프론트가 한다. 워커가 상태를 안 들고 있으므로
그게 맞는 자리다. 진짜 멱등이 필요해지면 그때 별도 커밋이다.

UI는 호출 횟수나 모델 종류를 전제하지 않고 최종 응답 하나만 받는다.
후보, 고르는 쪽 판정, 검사 결과는 화면에 절대 노출하지 않는다 —
`stages`에 실리는 것은 숫자뿐이고 대사는 하나도 안 실린다.
